# 蓝牙曲谱下发（ATK-BLE02）—— 实现说明

> 2026-10-30。对应代码：`fpga_gowin_project/src/` 里 `uart_rx` / `uart_tx` /
> `frame_parser` / `frame_tx` / `cmd_exec` / `event_ram` / `song_player` /
> `score_alloc` / `keymap` / `recorder` / `ble_line` / `ble_text`。
>
> 协议基线是 `PROTOCOL.md` v1.0（用户提供），**下面 §4 列出本工程和它的差异**，
> 看协议之前先看那张表。

---

## 1. 它能做什么

手机（安卓 Chrome 打开网页）→ 蓝牙 → FPGA：

| 功能 | 说明 |
|---|---|
| **传曲谱** | 选一个 `.sps` 文件 → 下载到 FPGA 的 BSRAM → 自动演奏（可循环） |
| **自定义键位** | 12 个物理键各指定一个音高（或禁用），整表 CRC32 校验后生效 |
| **录音回传** | 按"开始录制"随便弹 → "停止并传回" → 手机存成 `.mid` 文件 |

板上另外显示三行状态（键盘下方）：

```
BLE READY
EVT 1234      ← 已下载的事件数
REC 12        ← 本次录到的事件数
```

## 2. 硬件接线

模块串口固定 **115200 8N1 透传**，VCC 与 IO 电平都是 **3.3 V**。

USB-TTL（USB 转串口小板）**不在数据通路上**，它只把验收拆成三段。
同一个模块 + 同一个小板，**三种接法，别混**：

### 2.1 接法 A：USB-TTL 接 FPGA（PC 直连测试，蓝牙缺席）

```
PC ──USB── USB-TTL ──┬── TXD ──► A14   (ble_rx)
                     ├── RXD ◄── B13   (ble_tx)
                     └── GND ──── GND
```

- **只接三根**；小板的 3V3/5V **不要**接到板子（板子自己供电，两个电源会互顶）。
- 板上不插模块，也不插 SDRAM 子板。

### 2.2 接法 B：USB-TTL 接模块（AT 配置，一次性）

```
PC ──USB── USB-TTL ──┬── TXD ──► 模块 RXD
                     ├── RXD ◄── 模块 TXD
                     ├── GND ──── 模块 GND
                     └── 3V3 ──── 模块 VCC
```

- 小板上的 **3.3 V / 5 V 跳线必须选 3.3 V**（模块 UART 电平 ≤3.3 V）。
  小板没有 3.3 V 输出时，用板子 J13 的 +3V3 给模块供电，**GND 必须共地**。
- **TXD/RXD 交叉**；此时 FPGA 不参与。

### 2.3 接法 C：模块接 FPGA（正常使用）

**模块实际是 ATK-MW579D**（= ATK-MW579S 带底板版），6 脚排针，AT 指令与 ATK-BLE02 同一套。

| 模块引脚 | 名称 | 接到 | 说明 |
|---|---|---|---|
| 1 | VCC | **3.3 V** | 范围 3.3~5 V，只用 3.3 V |
| 2 | GND | GND | 必须共地 |
| 3 | TXD | **A14**（SDRAM0_DQ6） | FPGA 的 `ble_rx`，输入，内部上拉 |
| 4 | RXD | **B13**（SDRAM0_DQ4） | FPGA 的 `ble_tx`，输出 |
| 5 | STA | 不接 | 蓝牙连接状态输出 |
| 6 | **WKUP** | **悬空** | 低功耗唤醒 / **串口升级使能**，拉低可能进升级模式 |

手册明确：**通讯引脚仅支持 3.3 V 电平**（与 5 V 设备通讯要加电平转换），和 FPGA 的 `LVCMOS33` 正好匹配。

⚠️ **VCC 只能 3.3 V**。若模块内部没有 LDO 而给 5 V，TXD 会打 5 V 到 A14，超出 FPGA 输入额定值。
⚠️ 板载 USB-UART 的两根（`U15`/`V14`）已经接到板上的串口芯片，**不能**用。
⚠️ J13 上不能插 SDRAM 子板（12 键 + 4 编码器 + 这两根已经把脚占满了）。
⚠️ 模块的 STATE/LINK 指示灯不用接。

**模块一次性配置**（接法 B，脚本见 §3.2；手动方式：进 AT 模式后逐条发，最后 `AT+ENTM`）：

**进 AT 模式**（手册"1. 配置模式说明"，两种方法，推荐方法 2）：

```
静默 >100ms  →  发 +++a  →  模块回 a+ok     ← 方法2
（方法1：发 +++ 回 a，再发一个小写 a 回 +ok）
```

⚠️ 只发 `+++` 拿到 `a` 还没进去，**必须再发一个 `a`**；进去后 3 s 内要发命令，否则退回透传。

进 AT 模式后逐条发（每条以 `\r\n` 结尾）：

```
AT+NAME=BLE-PIANO-01
AT+UART=115200,8,0,1
AT+UARTTIM=1          ← 关键！出厂是 10 = 100 ms 打包延迟，不改状态回包会慢 0.1s
AT+HELLO=␣            ← 注意 '=' 后面要有**一个空格**；空参数会回 ERROR
AT+UUID?              ← 抄下三串 UUID，和下面默认值核对
AT+ENTM               ← 回到透传模式
```

默认 UUID（手册值，**TX 那串手册印错了一个 0**，以 `AT+UUID?` 实测为准）：

| 项 | 值 |
|---|---|
| 服务 | `9ECADC24-0EE5-A9E0-93F3-A3B50100406E` |
| 写（手机→模块） | `9ECADC24-0EE5-A9E0-93F3-A3B50200406E` |
| 通知（模块→手机） | `9ECADC24-0EE5-A9E0-93F3-A3B50300406E` |

> 2026-10-31 用 `AT+UUID?` 实测，三串与上表**完全一致**
> （手册把 TX 印成 `A3B503000406E`，多了一个 0，实测是 `A3B50300406E`）。
> 网页版不硬编码方向，按**特征属性**（write / notify）自动找，所以就算 UUID
> 和手册不一样也能用。

## 3. 上手步骤（按顺序，每段只引入一个变量）

先验 FPGA 侧，再配模块，最后才上手机。前一段全绿，后一段出问题就只剩接线/模块两种可能。

### 3.1 阶段 1：PC 直连验 FPGA（接法 A）

关掉串口助手 / Arduino IDE 等占串口的程序，然后：

```
py -3 tools/gen_frames.py                 # 生成 out/ 下的素材（自带自检）
py -3 tools/send_uart.py COM5 --ping      # 期望 ← STATUS OK
py -3 tools/send_uart.py COM5 --smoke     # 听到 C4 C4 G4 G4 A4 A4 G4
py -3 tools/send_uart.py COM5 --sps tools/out/twinkle.sps
py -3 tools/send_uart.py COM5 --keymap 72,74,76,77,79,81,83,73,75,78,80,82
py -3 tools/send_uart.py COM5 --rec-begin    # 之后弹 3 个音
py -3 tools/send_uart.py COM5 --rec-stop     # 打印录到的条数
py -3 tools/send_uart.py COM5 --rec 3 --save tools/out/rec_pc.sps
```

| 步骤 | 判据 |
|---|---|
| `--ping` | 收到 `STATUS OK`（16 B 帧 `AA5A 0180 …`） |
| `--smoke` | 听到七音；屏上 `BLE READY` → `BLE PLAY`，`EVT 0007` |
| `--sps` | 整首小星星；STOP 能停、loop 能循环 |
| `--keymap` | 上面的表是默认表**整体升八度**，一按就能听出音高变了 |
| `--rec-begin/--rec-stop/--rec` | `--rec-stop` 报的条数 = 弹的音数（**一音一条**，松开时补 dur）；`rec_pc.sps` 能再下回去重放 |
| 余量 | 用 `tools/out/chord4.sps --loop 255` 循环 4 音和弦，同时按住尽可能多的键，听是否削波（数字上限 12×30000÷16 = 22500 < 32767，不会饱和） |

> `--loop N` 的语义是**再重复 N 次**（0 = 只放一遍，255 = 无限循环），不是"循环开关"。

查端口：`py -3 -c "import serial.tools.list_ports as p;print([x.device for x in p.comports()])"`

### 3.2 阶段 2：AT 配置模块（接法 B，一次性）

```
py -3 tools/at_config.py COM5 --query     # 先确认进得去 AT 模式、看清当前值
py -3 tools/at_config.py COM5             # 写入 + 回读确认
```

脚本会等 350 ms 静默后发 **`+++a`** 进 AT 模式（收到 `a+ok` 才算进去；失败会自动退回
"`+++` → `a` → `a`"的方法 1），然后依次写 `AT+NAME` / `AT+UART` / `AT+UARTTIM=1` /
`AT+HELLO=␣`，回读核对，打印 `AT+UUID?` 的三串 UUID，最后 `AT+ENTM` 回到透传。

- **关键只有一条**：`AT+UARTTIM` 从出厂 10（100 ms 打包）改成 **1**（10 ms）。
  回读应看到 `+UARTTIM:1->10ms`。
- ⚠️ `AT+HELLO=` 空参数会 **ERROR**，`=` 后面必须有一个空格。
- 跳不过去时手动：`py -3 -m serial.tools.miniterm COM5 115200`。
- `AT+ENTM` 之后才生效；改过 `AT+UART` 的模块建议断电重上电一次。
- **做完把 TXD/RXD 从模块换到 FPGA**（接法 C），模块 VCC 改由板子 3.3 V 供。

### 3.3 阶段 3：手机蓝牙（接法 C）

**S0 静态检查**：模块先只接电源（TXD/RXD 不接）→ 上电，屏上键盘下方应显示
`BLE IDLE / EVT 0000 / REC 0000`。这行由 `ble_line` 用初值画，与蓝牙无关；
这里就错 ⇒ 烧的不是 v37（先看右下角 `BUILD V37`）。

**S1 PING**：手机连 `BLE-PIANO-01`。
- 有网页：`web/ble_piano.html` → "连接" → "PING（链路自检）"，日志出现 `← OK arg=0`。
- 没网页：装 **nRF Connect**，开通知特征，往写特征写 16 字节
  `AA5A010100000000000000000000C55F`，应收到
  `AA5A018000040000000000000000C992`。
- 不通先换 TXD/RXD 两根线（最常见），再怀疑别的。

**S2/S3 冒烟流与整曲**：网页"传曲谱"，判据同 §3.1。
**S4 键位**：12 个下拉改音高 → 下发 → 按键音高变；发错表 CRC32 → 屏上 `ERR 06`（旧表不变）；
连帧的 CRC16 都打坏则回 `0x01`（帧被丢、重新同步）。
**S5 录音回传**：开始录制 → 弹几个音 → 停止并传回 → 浏览器下载 `rec_*.mid`。

### 3.4 手机网页怎么打开（Web Bluetooth 要求安全上下文）

`http://192.168.x.x` 不算安全上下文，`navigator.bluetooth` 不会出现。按顺序试：

1. **PC 起本地 HTTP + Chrome 白名单**
   `cd web && py -3 -m http.server 8000`；
   手机 Chrome 开 `chrome://flags/#unsafely-treat-insecure-origin-as-secure`，
   填 `http://<PC的局域网IP>:8000`，Enabled，重启浏览器。
2. **adb reverse**（最干净，`localhost` 天然安全）：手机开 USB 调试，
   `adb reverse tcp:8000 tcp:8000`，打开 `http://localhost:8000/ble_piano.html`。
3. **`file://` 直开**：把 html 拷进手机 Download，用 Chrome 打开；不保证放行，不行退回 1/2。

网页三张卡片：**传曲谱** / **自定义键位** / **收录音**。

`.mid` 的时基是"1 tick = 1 ms"（tempo 500000 µs/四分音符、division 500），
任何 MIDI 播放器都能直接放。

### 3.5 自己转曲谱

```
py -3 tools/midi2sps.py 你的曲子.mid -o tools/out/song.sps --maxpoly 4
```

`--maxpoly 4` 是因为板上曲谱只有 **4 个专用声部**（超出的音会被丢掉）。

## 4. 和 PROTOCOL.md v1.0 的差异（重要）

| 项 | 协议原文 | 本工程 | 原因 |
|---|---|---|---|
| **KEYMAP 表长** | 128 项 | **12 项** | 板上只有 12 个物理键 |
| `table_crc32` 覆盖 | 128 字节 | **12 字节** | 同上 |
| 力度 `vel` | 1–127 参与发声 | **只保留在事件里，不参与发声** | 音源核没有力度输入 |
| `KEY`(0x30) 手机触屏发音 | 支持 | **未实现**（回 `ERR_CMD`） | v1 不做 |
| `PAUSE`/`RESUME` | 预留 | 未实现（回 `ERR_CMD`） | 协议本来就写 v1 不做 |
| `REC_*` 录音回传 | 无 | **新增**（见下） | 用户需求 |
| `GET_STATUS` 的 REC 态 | 无 | 回 `0x25` | 扩展 |
| `PLAY` 的 `tick_ms` | 用 BEGIN 下发的 | 同协议（`1..10`） | — |

### 新增指令（录音回传）

| CMD | 名称 | LEN | 载荷 | 回包 |
|---|---|---|---|---|
| `0x40` | REC_BEGIN | 2 | `tick_ms u16`（1..10） | `STATUS 0x00` |
| `0x41` | REC_STOP | 0 | — | `STATUS 0x00`，arg = 事件数 |
| `0x42` | REC_READ | 4 | `offset u16, count u16` | `STATUS 0x13`(arg=count) → N×`0x81` → `STATUS 0x14`(arg=offset+count) |
| `0x81` | RECDATA（FPGA→手机） | 8 | 与 §4.1 **事件记录完全同格式** | — |

`RECDATA` 的载荷就是 8 字节事件（delta/note/vel/dur/flags/rsv，小端），
所以**录下来的东西本身就是一份 `.sps`**，可以原样再下载回去重放。

⚠️ **录制和下载共用同一块事件 RAM**，不能同时进行：REC_BEGIN 会清空缓冲。
⚠️ REC_READ 的 `offset+count` 超过实际录到的条数时，多读出来的部分是**旧数据**，
   手机端以 `REC_STOP` 回的 arg 为准。

## 5. FPGA 侧实现要点（改代码前必看）

### 5.1 声部

- 键盘仍是原来的 **8 声部**（`voice_manager`），**一个字没改**；
- 曲谱另有 **4 个专用声部**（`u_voice8..11`），和键盘**永远不抢**；
- `mixer` 从 8 路扩到 12 路，`SUM_SHIFT` 仍是 ÷16。
  ⚠️ 最坏情况 12 路齐响 = 22500（69% 满量程），**上板要专门验一次不削波**。

### 5.2 曲谱的音高怎么进音源

`voice.v` 加了两个旁路：

| 端口 | 作用 | 谁用 |
|---|---|---|
| `km_notes/km_sel` | 用键位表代替 `note_map`，**八度仍生效** | 键盘 8 个声部 |
| `note_abs/note_sel` | 直接给频表索引，**绕开键位表和八度** | 曲谱 4 个声部 |

### 5.3 "踩过"的坑（改代码时别复发）

1. **事件记录的字节序有两套**：RAM 里是"小端整字"（delta 在 `[15:0]`），
   线上是"第 0 字节 = delta 低字节"。下载方向要**倒一次**，回传方向也要**再倒一次**。
   弄反了不会报错，只会听到音高全错。
2. **`event_ram` 的读地址必须组合给出**（`assign raddr = idx`）。用寄存器给地址会
   差一拍，整首歌的事件全部错位一格。
3. **`STATUS` 回包和 `RECDATA` 走同一条发送队列**，同一拍只能进一个；
   `REC_READ` 的最后一条 `0x14` 必须隔一拍发，否则会被 RECDATA 挤掉。
4. **事件里的 `note` 是 MIDI 音号，不是频表索引**（2026-10-31 上板实测的 bug）。
   三条通路必须同一口径：`.sps` 下载的 note 是 MIDI（`song_player` 内部减 24 得索引）；
   手机端把 `RECDATA` 的 note 直接写进 `.mid`；而 `keymap` 的输出**已经是索引**，
   所以 `recorder` 必须 `+24` 再写（`recorder.v` 的 `kn_midi`）。
   弄错不报错，只会"录完再放回去低两个八度"——而且 `tb_ble_m3` 当年把索引写成了
   期望值，仿真一直是绿的。
5. **`sample_strobe` 的扇出贴着 LW 阈值**（工程里那条"时钟表多一行就不跑"的铁律）。
   加这 4 个曲谱声部时直接把它顶过了线：PnR 报 `LW 1/8`、`n155_3 | LW`，
   而综合/布线/时序报告**全部正常**。
   ⇒ 曲谱那 4 个声部改用 `strobe1024.v` **本地自产**的同频节拍，不挂全局那根。
   **以后任何模块都不要往 `sample_strobe` 上加负载**，要采样节拍就自己产生。
6. **屏幕的波形 / 李萨如用"有没有按键"做绘制门控**（2026-10-31 上板发现）。
   `display_top.v` 里描迹与李萨如原来只看 `any_key || fx_any_s`（物理按键 / 有湿声），
   而**曲谱播放没有任何物理键按下** ⇒ 播放时描迹被钉在中线、李萨如不画，
   只有频谱（那一路不门控）在动 —— 症状就是"只显示了频谱图"。
   ⇒ v39 加 `snd_on` 端口（= `song_player.busy`，两级同步进 pclk 域），
   门控改成"按键 / 湿声 / 播放中"三选一（`draw_on`）。
   **以后凡是给显示加"门控"，都要同时问一句：曲谱与录音回放会不会经过这里。**
7. **同音重触发会让止音槽失效 ⇒ 整首歌越叠越多、曲终不静音**（2026-10-31 上板发现）。
   `song_player.v` 的同音复用分支原来只写 `oaX`（续期）而**没重置 `ovX`**；
   而真实曲谱是 `dur == 下一音的 delta`（小星星：都是 500 ms）⇒ 下一音的起音时刻
   正好等于上一音的止音时刻，止音检查先把槽清掉，S_RUN 又没置回来 ⇒ 槽作废、
   这个音**永远没有止音** ⇒ `score_alloc` 的门控一直是 1（持续音色停在 S_SUS）。
   曲谱里是成对的重复音（60,60 / 67,67 …）⇒ **每对泄漏一个声部**，4 个声部很快占满，
   之后每次偷声部只换音高、门控不落 ⇒ 越叠越多，对结束只剩最后四个音一直响。
   修法（v40）：四条同音分支都补 `ovX <= 1'b1`；`start`/`done` 各补一次 `panic`
   （起播前清残留、曲终强制静音）。
   ⚠️ `tb_ble_m2` 当年一直是绿的，因为它的测试曲没有"重复音 + dur == 下一音 delta"，
   而且它只核对 `off` 脉冲时刻、**从不检查 `s_gate`**。现在补了 T3b（重复音用例 +
   曲终 `s_gate==0`），改前应 FAIL（已做负对照验证）。
8. **播放态的显示余辉**：`poly` 原来只数物理按键 ⇒ 播放时 `poly=0`，
   描迹每帧直接跳最新一窗，相位一变就是"多条左右错开的线"。
   v40：`disp_poly` 并入 `pl_busy`；新增 `snd_evt_tgl`（每个音符事件翻转一次）经
   三级同步 + 检沿得到 `snd_e`，与 `key_changed` 合成 `chg`，驱动余辉播种/重捕。
9. **录音回传"有的音漏掉"是**页面**的错，不是记录器**（2026-10-31）。
   原页面一次性 `REC_READ(0, 8192)`，再用 200 ms 定时器"收到第一条就 buildMidi"：
   ① FPGA 用 115200 连续吐帧（~1.4 ms/条），BLE 一个连接间隔只走几十字节 ⇒ 模块缓冲溢出、随机丢帧；
   ② 200 ms 就抢先打包 ⇒ 尾部音符全丢。
   现在：REC_STOP 回包 `arg` = 事件总数 → **每块 16 条**请求 → **等到 `0x14` 才要下一块**

   记录器本身用 `tb_rec` 验过：同拍双键、按住一个再按另一个、同拍双松，**4 条事件逐字段正确**。
10. **静音时波形面板留空 + 松键后继续画衰减尾音**（v41）。

    （⚠️ 静音那一项 v43 改成跑满一整帧 120 万拍，见第 13 条 (a)）。
11. **左侧小键盘黑键按下改成青色**（v41）：原来白键/黑键按下都是橙 `FF8000`，

12. **钢琴余波被下一个键抢掉 / 余波显示太短**（v42，两处）
    (a) `voice_manager` 的 `last_free`（键已松开就复用该声部）**优先于** `idle_mask`
        （包络真正归零）：钢琴松手后还有 1.36 s 的衰减尾巴，新键却抢走同一个声部、
        重启包络 ⇒ **余波被切掉**（用户："旧的余波应该和新音叠加才对"）。
        改成 `last_free && v_idle[last_sel]`。**滑音不受影响**——它由上面的
        `glide_mode` 分支无条件接管。`tb_vm_alloc` 四条用例全 PASS，负对照（改回旧写法）FAIL。
    (b) `display_cond.active` 的门限原来取 **100**（那是 AGC 的**增益**冻结门限，不是"有没有声"）：

        改成 **16**（≈1.0 s）。想调残留时长就改这个数（越小越长）。
    ⚠️ v43 起这个"长门限"**只给单独钢琴**，见第 13 条 (b)。
    ⚠️ 副作用（正确行为）：快速连续弹奏不再"复用同一个声部连成一片"，

13. **v43：四个显示问题（用户上板实测）**
    (a) **切到任意效果器后，静音时波形面板仍画一条中线**。`draw_on` 里含 `fx_any_s`
        （v41 之前靠它"钉住"湿声尾音）。但 v41 的 `aud_on_s` 本来就取自**效果器之后**的
        `mix_fx`：有湿声=1、真静音=0 ⇒ `fx_any_s` 已完全冗余，留着只会把静音当"有声音"。
        删掉它；`fx_any_s` 仍保留给 `idle_max`（21 ms 快速自由刷新）。
        ⚠️ 顺带发现 `tb_scope_onset` 原来的静音检查只跑 20 万拍（50 MHz 下不足一帧），
        可能整段落在消隐区 ⇒ **检查是瞎的**。现在跑 120 万拍，负对照实测
        `wave_hit=4096`（确实在画中线）⇒ 会 FAIL。
    (b) **余波只给"单独钢琴"**。`display_cond` 新增输入 `tail_long`，门限分两档：
        1 → `avg>16`（≈1.0 s），0 → `avg>100`（≈0.2 s）。`top.v` 给 1 的条件是
        **音色=钢琴 且 三个效果器全关**（用户："严格单独钢琴"）。
        `tb_disp_active` 实测 265.7 ms / 110.3 ms（差 155 ms）；负对照（两档都用 16）FAIL。
    (c) **按下瞬间的"横向重影"**。换键后的第一窗原来用 `first_win` 从**当前采样**起，
        而其余每窗都把"真实过零点"放在窗内第 256 点（屏幕中线）⇒ 那一帧波形横移半屏；
        单键每帧直接换窗，眼睛看到的就是一闪的双影。现在**所有窗口一律等 `scope_trig`**
        （删掉 `first_win`），并把 `chg` 时的 `idle_cnt` 从 8191 改回**归零**
        （原来会"下一个采样立即自由运行一窗"，相位随机，松键时同样再闪一次）。
        代价：新波形晚 ~15 ms（约 1 帧）出现。`tb_scope_onset` 的 V43-B 判据：
        "无触发时不许开窗" + "首窗起点 = 写指针−268"，负对照两项都 FAIL。
    (d) **松开一个键马上弹另一个音时没有余辉优化**。`disp_poly` 原来只数物理按键；
        v42 起旧音的衰减尾音与新音真的叠加，但按键只有 1 个 ⇒ `poly=0` ⇒ 每帧跳最新窗，
        合成波相位乱跳。现在 `disp_poly` 并入"**还在响的声部数 ≥2**"（`~v_idle` 的个数），
        并在 `top.v` **寄存一拍**再进 pclk 域（避免把 8 位加法叠进余辉累加器的组合路径）。
14. **v44：延迟+混响开着时，余音（所有音色）的波形/李萨如整块不画**
    v43 把 `draw_on` 里的 `fx_any` 删掉之后，描迹只剩 `aud_on`（= `display_cond.active`）一个来源；
    而效果器档的门限是 `avg>100`。实测湿声尾音比干声低得多
    （`tb_fx_xprobe` 量到：尾音瞬态只有 ~50~150 码 ⇒ `avg ≈ 30~90`）⇒ 一松键立刻掉到 100 以下，
    门控归 0，面板整块留空。**而且** AGC 在 `avg≤100` 就冻结在 ×16，即使门控放行也只有 3~11 px。
    v44 两处一起改（都在 `src/display_cond.v`）：
    ① `active = (tail_long || fx_n!=0) ? (avg>16) : (avg>100)`
       —— 开效果器时跟随湿声尾音一直到很轻；
    ② AGC：开效果器时冻结门限 100→8、档位由 ×16 扩到 **×256**（gsh 4→8，回差带按 2.5:1 递减），
       尾音全程保持 ~40 px 可辨识；gsh 5..8 **只在 `fx_n!=0` 时可达** ⇒ 关效果器时逐位不变。
       ③ 补一条边角：**效果器全关的同一拍把 gsh 拉回 4**（`if (!fx_mode && gsh>4) gsh<=4`）。
       否则"尾音很轻时关掉效果器"会把 gsh=8 留在寄存器里，而冻结门限 avg>100 又让 FSM
       不更新 ⇒ 下一个音有 100~300 ms 是 ×32…×256 的超大波形。正常演奏 gsh≡4，这条恒不触发。
    ⚠️ 取舍：**"钢琴+效果器"也会出现 1 s 量级的长尾** —— 那是混响/延迟本身在响，
    不是多出来的余波。上一轮"严格单独钢琴"与本轮"余音要看得见"在物理上是同一件事，
    按"真的有声就画"为准。
    验证：`tb_disp_effect_tail`（灌 τ=0.25 s 衰减的 1 kHz 正弦模拟湿声尾音）——
    新代码 active **1.05 s**、600 ms 处峰值 **8000 码**；负对照（改回 `avg>100` + 上限 ×16）
    **0.59 s / 2592 码 ⇒ FAIL**。`tb_disp_active`、`tb_agc_onset` 回归通过。
    ⚠️ 附带发现：`tb_fx_tail`/`tb_fx_xprobe` 里 fx 的延迟线在 ModelSim 中会在音符开始后
    某个时刻突然输出 X（RAM 已逐个清零、`din` 一直有效，原因未查明；硬件 BSRAM 上电清 0、
    不存在 X）⇒ 这两个 TB 只当"电平探针"用，**不作为判据**。

17. **v47：录音回传"每块固定少一条" —— `frame_tx` 队列满时覆写 f3**（2026-11-01）
    上板日志（v46 固件 + 分块页面）：要 4 条只回 3 条、要 6 条只回 4 条，
    **重发多少次都一样**，而 `0x14 REC_END` 照样到齐 ⇒ 不是随机丢包，是确定性丢帧。
    根因在 `cmd_exec.v` + `frame_tx.v`：
      · `frame_tx` 的队列 4 深，`fc == 4` 时来的 `tx_req` 会**写进 f3 覆盖最年轻的那条**
        （不报错、不置满标志）；
      · 录音流恰好把队列灌满（`0x13` + N×RECDATA），最后一条 RECDATA 入队后 `fc=4`，
        紧接着 `st2_pend` 发出的 **`0x14` 状态帧**没有检查 `tx_ready` ⇒ 把最后一条数据顶掉。
    修法（只动 `cmd_exec.v`，`frame_tx.v` 一个字不改）：
      ① 发送侧改成 `else if (st_valid && tx_ready)` —— 队列没空位就不发；
      ② 主状态机末尾 `if (st_valid && !tx_ready) st_valid <= 1'b1;` —— 没被接收就保持、
         下一拍再发（`st_valid` 仍只在**同一个** always 块里驱动，不会多驱动）。
    ❌ **这个固件改法已回退（2026-11-01 上板）**：含该改动的 v47 三套布局
       （place 2 → 54.4 MHz、place 1 → 65.1 MHz、place 3 → 70.3 MHz）**HDMI 全黑**；
       同源、只差这一处的 v46 位流**正常点亮**。机理不明（这段逻辑只在 UART 命令通路），
       但二分证据明确 ⇒ 固件回退到 v46 原样（`cmd_exec.v` 里留了警示注释）。
    ⚠️ `tb_ble_m3`（T6 回传）改前改后都 PASS —— 这组 3 条用例恰好没把队列灌到 4 深，
       **负对照没有触发点**；这一条只能靠上板日志判定（已按该日志定位）。
    ✅ **最终修法改在网页端**：每次 REC_READ **多要一条**（`ask = cnt + 1`，只取前 cnt 条）。
       队列满时被 0x14 顶掉的正好是那条多余的；队列没满时多出来的那条也只是被忽略、
       下一块会重新取。两种情况下都能拿满 cnt 条，**不需要改固件、不需要重烧**。
    页面（`web/ble_piano.html`）同步改：
      · 分块 16 → **8** 条；等 `0x14` 的超时 **5000 → 1200 ms**；
      · 块内丢帧时**整块重发**（最多 3 次），重发前 120 ms 让模块吐空；
      · 连续 3 次仍不完整 ⇒ 块**减半**（8→4→2→1）从同一位置重来，连续 4 块干净再翻倍；
      · 必须"先见到 `0x13` 再认 `0x14`"，数据只在 `0x13` 之后收 ⇒ 上一块迟到的包不污染下一块；
      · `dur=0`（按到"停止"还按着没松的音）写 **250 ms**（原来 `|| 1` ⇒ 1 ms **听不见**）；
      · 日志打首尾各 3 条事件（`音号@+间隔/时长`），便于区分"丢帧"和"时间轴错"。
